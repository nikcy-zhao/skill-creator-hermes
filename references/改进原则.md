# 改进原则

依次对检验报告/用户反馈中的问题执行：

1. **真正理解用户。** 反馈简短或带挫败感时先别照字面打补丁——看用户实际写了什么，找到判断标准、分清局部还是系统性毛病，再决定改哪里
2. **从反馈泛化。** 别打贴着示例修的过拟合补丁；问题顽固时先换思路再落笔
3. **合并重复功能（改进任何技能时必做）。** 按 `references/重复形态清单.md` 逐项排查；清单外的新形态判明后补录进清单。对照必须基于本次通读双方原文，禁止凭印象判"应该不重复"
4. **目录改进**：标准目录之外的目录重新归类并删；无法归类的向用户说明，由用户定
5. **删除废话**：已判明的废话形态见 `references/废话形态清单.md`
6. **保持精简。** 删纯解释性冗余；执行时才展开的编排细则外挪 references（正文留一行指针与门槛词），当场要用的判据留正文；一次改到位留余量，不贴线交付。务必读执行记录（`~/.hermes/state.db` 的 messages 表、工作区 `stdout.log` 与 `usage.json`）而非只看最终输出；空转指纹：重复相同调用、报错后原样重试、token消耗较基线虚高。判定某句引发空转须改后重跑对比，空转消失才算坐实
7. **死资产同步清除**：精简后反向扫描——references/scripts/assets 下每个文件按文件名全库 grep，零引用且无目录级消费即为死资产，删；指向已删文件的引用同步清
8. **改代码后反查文档（交付前必做）**：改动 scripts/ 后，反向排查 SKILL.md 与 references 中引用该行为/字段/输出结构的全部表述——已内建进脚本的旧表述按废话形态⑧改写或删；输出结构变化同步 schema 示例
9. **术语可执行（任何改动前先过这道）**：正文每处表述，换一个未读过对话历史的模型也能不猜就照做。判定：① 是否为聊天比喻（如「同弧」「患者技能」）——比喻不入正文，改用正文已有术语（如「4↔5 循环」）或白话直说；② 是否为未定义黑话/生造缩略语——首次出现必须带一句白话定义，或换成平实说法；③ 已有定义的术语（「死资产」「空转」等在本库有定义处）沿用不换。改术语须全文 grep 旧名清零，禁止两叫并存

## 交付门槛

技能改进的零残留三查与逻辑一致性自检，缺一不算完成；判定只认本次通读证据，抽查与假设无效。

**零残留三查**：

1. **文件全消费**：scripts/references/templates/assets 下每个文件都有真实消费方——或被脚本执行/读取，或被 SKILL.md 正文按路径指引。判定标准是与脚本的输入输出源码逐一对照，不认"看起来该被用"。孤儿文件（零消费）即删。
2. **路径全对齐**：SKILL.md 与 references 里出现的每个路径、字段名、命令 flag，都能在盘上找到文件、在脚本源码里找到消费点；不存在的路径（幽灵文件）即删或改写到真消费方。
3. **副本全同步**：改动覆盖源库与部署两份副本，`diff -r` 一致；引用被改文件的所有位置（含其他技能的互引）同步更新。

**逻辑一致性自检**：同一事实（节数/数量/版本号/路径/规则）全文只能有一个说法。高发：引入新来源旧数字没清、同一规则两处只改一处、条款适用范围改了旧限定词还在、Quick Reference 列表与 Procedure 重复（步骤里已有"路径+何时读"的条目即重复）。自检法：改完任何带硬数字或范围词的表述后，全文 grep 旧表述，有残留即统一。
